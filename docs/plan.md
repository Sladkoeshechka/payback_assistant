# Payback — план разработки v1

> Рабочий документ. Источники требований: [`spec.md`](spec.md), [`planfix-notes.md`](planfix-notes.md).
> Статус: черновик плана, составлен 02.10.2026.

---

## 0. Главное ограничение по срокам

**Пробный период ПланФикса истекает 12.10.2026 — через 10 дней.** После этого без оплаты Plan A (~463 ₽/место, нужно 3 места) пропадает доступ к REST API, а значит и возможность:

- снять фикстуры реальных ответов API в `tests/fixtures/` (на них строится вся Этап-2 проверка клиента);
- закрыть 9 открытых вопросов из `planfix-notes.md` §11 (ID статусов, формат `comments/list`, «эхо» вебхуков, `POST /task/list`).

Поэтому план **начинается не с кода, а с разведки** (Этап 1). Всё, что требует живого аккаунта, делается в первые дни; остальные этапы затем идут офлайн на фикстурах, независимо от того, продлён аккаунт или нет.

## 1. Этап 1 — Разведка ПланФикса и сбор фикстур (приоритет, до 12.10)

Единственный этап с жёстким дедлайном. Код здесь минимален: скрипты + сохранённые ответы.

**Задачи**

1. Достроить настройку тестового аккаунта до состояния из `spec.md` §7: вебхук-сценарии на остальные 4 статуса («Уточнение», «Отклонено», «Требует доработки», «Компенсировано» — настроен только «Одобрено»).
2. Выяснить и записать в `planfix-notes.md` §10 **ID всех 7 статусов** (известны 101, 103, 108).
3. Проверить «эхо»: приходит ли вебхук, когда статус меняет сам бот через API. Определяет, нужна ли дополнительная защита помимо сравнения с локальным статусом.
4. Разобрать формат `POST /task/{id}/comments/list`: автор, служебный/человеческий комментарий, порядок сортировки.
5. Проверить `POST /task/list` с фильтром по Объекту и периоду (нужен для `/report` в roadmap, но формат фильтра лучше снять сейчас).
6. Проверить поведение повторов вебхука при ответе ≠ 200.
7. OpenAPI ПланФикса **не** класть в репозиторий (чужая спека): при необходимости смотреть https://help.planfix.com/restapidocs/swagger.json .
8. **Снять фикстуры** в `tests/fixtures/planfix/`: успешные и ошибочные ответы на каждый метод из `planfix-notes.md` §6 — создание задачи, чтение задачи с customFieldData, смена статуса, загрузка и прикрепление файла, добавление и чтение комментариев, `user/list`, `customfield/task`, `directory/{id}`, `directory/{id}/entry/list`, ответ 202, ответ `{"result":"fail"}`, scope denied.

**Артефакты:** `scripts/try_planfix.sh` (без токенов), `tests/fixtures/planfix/*.json`, обновлённые §10–11 в `planfix-notes.md`.

**Критерий готовности:** список «Осталось проверить» в `planfix-notes.md` пуст или каждый пункт помечен как сознательно отложенный; клиент ПланФикса можно писать и тестировать без доступа к аккаунту.

## 3. Этап 3 — База данных

**Задачи**

1. Модели SQLAlchemy 2.0 (declarative, типизированные) по `spec.md` §8: `users`, `invites`, `expenses`.
2. Локальный статус заявки как `Enum`: 7 статусов ПланФикса + «Ожидает отправки».
3. Уникальность чека по ФН/ФД/ФП. Поля nullable (заявки без чека и с ручным вводом) → **частичный уникальный индекс** `WHERE fn IS NOT NULL`, иначе NULL-строки конфликтуют по-разному в PostgreSQL и SQLite.
4. Async engine и `async_sessionmaker`, сессия на один апдейт/запрос.
5. Репозитории: `UsersRepo`, `InvitesRepo`, `ExpensesRepo` — узкие методы под сценарии, без «универсального CRUD».
6. Alembic: инициализация, первая миграция, `alembic upgrade head` как шаг запуска контейнера.
7. Тесты репозиториев на SQLite in-memory + отдельный прогон миграций.

**Критерий готовности:** миграции накатываются и на SQLite, и на PostgreSQL; тест на дубликат чека проходит на обеих БД.

## 4. Этап 4 — Клиент ПланФикса

Самый насыщенный модуль; пишется целиком на фикстурах Этапа 1.

**Задачи**

1. `planfix/client.py`: `httpx.AsyncClient`, базовый URL `{account}/rest`, `Authorization: Bearer`, таймауты.
2. Повторы: сетевые ошибки и 5xx — экспоненциальная задержка, до 3 попыток. **202 — успех.** `{"result":"fail"}` → типизированные исключения (`PlanfixScopeDenied`, `PlanfixNotFound`, `PlanfixError`), чтобы сервисы различали «нет прав» и «недоступен».
3. `Idempotency-Key` — детерминированный `uuid5` от локального ID заявки.
4. Методы по таблице `planfix-notes.md` §6: `create_task`, `get_task`, `update_task`, `upload_file`, `attach_file`, `add_comment`, `list_comments`, `list_users`, `get_task_custom_fields`, `get_directory`, `list_directory_entries`.
5. Сериализация значений полей (`planfix/fields.py`): число, строка, флажок, дата `{"date": "ДД-ММ-ГГГГ"}`, запись справочника `{"id": key}`; чтение — обратное преобразование. Пользовательские поля запрашиваются только при перечислении ID в `fields`.
6. Справочники: ID поля «Название» берётся из `GET /directory/{id}`, у записей название лежит в `customFieldData`, ключ — `key`.
7. Проверка схемы при запуске (`planfix/schema.py`): `GET /customfield/task`, сверка ID и типов полей из настроек, извлечение `directoryId` для «Категории» и «Направления затрат». При несоответствии — отказ стартовать с перечислением недостающего.
8. Кэш справочников: TTL 10 минут, при недоступности ПланФикса отдаётся последняя успешная версия, ручной сброс (`/refresh`).
9. Тесты на `respx` поверх фикстур: счастливые пути, 202, 5xx + повтор, fail-ответы, пустой справочник.

**Критерий готовности:** клиент покрыт тестами без сети; проверка схемы ловит подменённый ID поля и неверный тип.

## 5. Этап 5 — Распознавание чеков

**Задачи**

1. `receipts/qr.py` — интерфейс декодера с двумя реализациями: **OpenCV `QRCodeDetector` (основная)** и pyzbar (опциональная). Причина отхода от ТЗ: pyzbar — ctypes-обёртка над `libzbar.so`, которой нет в этом окружении и которую без root не поставить; OpenCV работает без системных зависимостей. В Docker-образ ставится `libzbar0`, и pyzbar включается флагом как второй проход. Задел под WeChat-детектор (roadmap v1.3) — третья реализация того же интерфейса.
2. Запуск декодирования через `asyncio.to_thread`.
3. `receipts/fiscal.py` — парсинг фискальной строки QR (`t`, `s`, `fn`, `i`, `fp`, `n`) в датакласс: сумма, дата-время, ФН, ФД, ФП. Терпимость к вариантам формата даты и разделителя суммы.
4. Валидация (`receipts/validation.py` или `services/validation.py`): сумма `0 < x ≤ MAX_AMOUNT`, дата не в будущем, возраст ≤ `MAX_RECEIPT_AGE_DAYS`, лимит `NO_RECEIPT_MAX_AMOUNT`; размер ≤ 15 МБ, только JPEG/PNG. Сообщения об ошибках — ровно из `spec.md` §4.2.2.
5. `scripts/generate_receipts.py` — синтетические чеки с QR; набор в `tests/fixtures/receipts/` (валидные, повёрнутые, размытые, без QR, битая строка).

**Критерий готовности:** юнит-тесты парсера и валидации; распознавание проходит на синтетическом наборе, на «плохих» фото корректно возвращает «QR не найден».

## 6. Этап 6 — Бот: каркас, регистрация, управление людьми

**Задачи**

1. `bot/` — `Dispatcher`, `MemoryStorage` для FSM, `Bot` с опциональным прокси из `PROXY_URL`, роутеры по сценариям.
2. Middleware: сессия БД, загрузка пользователя по Telegram ID, проверка роли и активности, перехват ошибок, логирование апдейтов.
3. `/start`: bootstrap владельца по `OWNER_TELEGRAM_ID`, вход по коду приглашения, ввод имени и фамилии, меню по роли.
4. Приглашения: `/invite` (сотрудник/руководитель), одноразовый код, 72 часа, ссылка `?start=<код>`, уведомление пригласившему, отказ при повторном переходе.
5. `/staff`: список подчинённых (активных и отключённых) и активных ссылок, отзыв ссылки, отключение/включение сотрудника, «Связать с ПланФиксом» (`POST /user/list` → выбор → `planfix_user_id`).
6. `/help`, `/refresh`, `/my`, `/pending`.
7. `DEV_MODE` включает только fallback на FakePlanfix для локальной отладки (без переключения ролей в боте).
8. `bot/texts.py` — все тексты в одном месте (готовность к i18n и ревью формулировок).
9. Тесты хендлеров через `dp.feed_raw_update` на основных диалогах.

**Критерий готовности:** на реальном боте проходится приглашение → регистрация → меню; сотрудник не видит команд руководителя.

## 7. Этап 7 — Подача заявки

**Задачи**

1. FSM подачи: фото → распознавание → (переснять / ввести вручную) → категория → направление → комментарий → карточка подтверждения → отправка.
2. Проверка на дубликат по ФН/ФД/ФП с сообщением «Этот чек уже подан …».
3. «Исправить»: выбор поля, запрет правки суммы и даты, распознанных по QR.
4. Поток «Трата без чека» (`ALLOW_NO_RECEIPT`): обязательный комментарий, лимит суммы, опциональное подтверждение, флажок «Без кассового чека».
5. `services/submission.py` — создание задачи как последовательность шагов с сохранением прогресса: локальная запись → `POST /task/` → `POST /file/` → attach → номер задачи и `planfix_file_id` в БД. По сохранённым ID видно, какие шаги уже выполнены, — дожимает фоновая задача.
6. Обработка краёв из `spec.md` §4.2.8: `/cancel`, новое фото поверх черновика, недоступный ПланФикс, сотрудник без связанного руководителя, пустой справочник категорий.
7. Тесты сервиса с `FakePlanfix` / `FakeNotifier`, включая падение на каждом из шагов 5.

**Критерий готовности:** заявка с фото и без чека доходит до задачи в ПланФиксе с правильными полями и вложением; обрыв на любом шаге дожимается без дублей.

## 8. Этап 8 — Согласование и уточнения

**Задачи**

1. Сообщение руководителю: данные заявки, фото, пометка «⚠️ Без кассового чека», кнопки.
2. «Одобрить» / «Отклонить» (запрос причины) / «Вопрос» (запрос текста) → `POST /task/{id}` смена статуса + комментарий в задачу + уведомление сотруднику.
3. Проверка прав на стороне бота: руководитель решает только по своим подчинённым, кнопка не срабатывает дважды (идемпотентность по текущему статусу).
4. Ответ сотрудника в статусе «Уточнение»: текст или фото → комментарий (фото — файлом) → статус «На согласовании» → новое сообщение руководителю.
5. Ответ в статусе «Требует доработки» → комментарий → статус «Одобрено».
6. `services/notifications.py` — единый слой уведомлений, отделённый от aiogram интерфейсом.
7. Тесты переходов и прав, включая попытку решить чужую заявку.

**Критерий готовности:** все переходы из `spec.md` §5 проходят в тестах; повторное нажатие кнопки не меняет статус дважды.

## 9. Этап 9 — FastAPI, вебхуки, единый процесс

**Задачи**

1. `api/app.py`: FastAPI, `/health`, `lifespan` — проверка схемы ПланФикса, старт polling aiogram фоновой задачей, корректное завершение с ожиданием фоновых задач.
2. `POST /webhooks/planfix`: сверка секрета через `hmac.compare_digest`, 403 без него, **немедленный 200**, обработка в фоне.
3. Обработчик: перечитать задачу (`GET /task/{id}`), не доверять статусу из тела; если статус совпал с локальным — игнор (отсечение повторов и «эха»); иначе обновить локальный статус, при необходимости прочитать последний комментарий, уведомить сотрудника, убрать кнопки у руководителя и дописать «Решение принято в ПланФиксе».
4. Маппинг «название статуса → локальный статус» для диагностики, при неизвестном статусе — лог, а не падение.
5. Тесты: подпись/секрет, быстрый ответ, идемпотентность повторного вебхука, цепочка «Одобрено → К выплате → Компенсировано».

**Критерий готовности:** эндпоинт отвечает < 100 мс, повторный вебхук не вызывает повторных уведомлений; `main.py` поднимает бота и API одним процессом.

## 10. Этап 10 — Фоновые задачи и надёжность — **готово**

Закрыт по факту пилотной надёжности. Несделанное перенесено в [§15 Roadmap](#15-roadmap-после-этапа-10).

**Сделано**

| Шаг | Суть |

## 13. Вопросы и отступления от ТЗ

Требуют решения; по каждому дана рекомендация, работа по ним не блокируется.

| Вопрос | Рекомендация |
|---|---|
| **Версия Python.** ТЗ говорит 3.12, локально доступен только 3.14.4 | Разрабатывать на 3.14, в `pyproject` поставить `requires-python = ">=3.12"`, базовый образ — `python:3.14-slim`, чтобы прод и разработка совпадали. Обновить §8 ТЗ |
| **pyzbar** недоступен локально (нет `libzbar`, нет root) | OpenCV `QRCodeDetector` — основной декодер, pyzbar — опциональный второй проход в Docker (см. Этап 5) |
| **`PROXY_URL`** есть в `.env`, но не описан в ТЗ | Добавить в `Settings` и в таблицу переменных ТЗ как опциональный прокси для Telegram API |
| **Формат `comments/list`** неизвестен до Этапа 1 | Спрятать за адаптером `planfix/comments.py` с нормализованной моделью комментария — Этап 8 не блокируется |
| **Язык документации** | Проектные документы — русский, код, коммиты и docstrings — английский. Этот план могу перевести на русский целиком или вести дальше по-английски |
| **Локальная PostgreSQL** | По умолчанию Postgres (`make db-up`, `make test` → `payback_test`). SQLite — opt-in (`make test-sqlite` / `DATABASE_URL=sqlite+…`) |

## 14. Порядок и зависимости

```
Этап 1 (разведка, до 12.10) ──┐
Этап 2 (каркас) ──────────────┼──▶ Этап 4 (клиент ПланФикса) ──┐
            └──▶ Этап 3 (БД) ─┘                                ├──▶ Этап 7 (подача) ──▶ Этап 8 (согласование) ──▶ Этап 9 (вебхуки) ──▶ Этап 10 (надёжность) ──▶ Этап 11 (Docker) ──▶ Этап 12 (приёмка)
            └──▶ Этап 5 (чеки) ───────────────────────────┐     │
            └──▶ Этап 6 (бот: роли, приглашения) ─────────┴─────┘
```

Этапы 3, 5 и 6 независимы друг от друга и могут идти в любом порядке после Этапа 2. Этап 1 не зависит ни от чего и выполняется первым из-за дедлайна пробного аккаунта.
