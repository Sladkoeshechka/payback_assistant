# Payback — согласование расходов сотрудников через Telegram для ПланФикса

> **Статус:** ТЗ для разработки v1, версия 0.8
> Документ одновременно служит техническим заданием для v1 и README будущего репозитория.
> Всё, что касается ПланФикса, проверено вручную на пробном аккаунте; подробности и примеры запросов — в [`planfix-notes.md`](planfix-notes.md).

---

## 1. Проблема

В малом бизнесе сотрудники регулярно тратят деньги на работу: материалы, расходники, топливо, такси, парковка. Чаще всего это выглядит так:

- чек присылают руководителю в личные сообщения или не присылают вовсе;
- непонятно, кто и когда одобрил трату;
- в конце месяца бухгалтер не может сверить расходы, часть чеков потеряна;
- сотрудник не знает, когда ему вернут деньги.

**Для кого:** компании на 5–50 человек, которые уже работают в ПланФиксе и у которых есть «полевые» сотрудники — строительные и ремонтные бригады, сервисные компании, клининг, небольшая розница и общепит, агентства с выездами.

## 2. Решение

Telegram-бот, через который:

1. **сотрудник** отправляет фото чека, а бот сам распознаёт сумму и дату по QR-коду;
2. **руководитель** одобряет или отклоняет трату одной кнопкой прямо в Telegram;
3. **бухгалтер** получает в ПланФиксе проверенный реестр трат и отмечает выплату.

Каждая трата — это задача в ПланФиксе со своими статусами, полями и историей. Изменения синхронизируются в обе стороны: действие в боте меняет задачу, а изменение задачи в ПланФиксе приходит уведомлением в бот.

**Ключевые преимущества:**

- полевым сотрудникам **не нужен аккаунт в ПланФиксе** (нет лишних платных мест);
- дубликаты чеков отсекаются автоматически по фискальным данным;
- решение разворачивается одним `docker compose up` на дешёвом VPS.

## 3. Роли

| Роль | Что делает | Где работает |
|---|---|---|
| **Сотрудник** | Подаёт чеки, отвечает на уточнения, досылает документы, смотрит статусы своих заявок | Только бот |
| **Руководитель** | Приглашает сотрудников и других руководителей по ссылкам; одобряет, отклоняет или уточняет траты своих сотрудников; смотрит отчёты | Бот (приглашения и решения), ПланФикс (отчёты) |
| **Бухгалтер** | Проверяет оформление одобренных трат, возвращает на доработку, отмечает выплату | Только ПланФикс |

В боте есть две роли: сотрудник и руководитель. **Бухгалтера в боте нет**: он работает в ПланФиксе, заявки приходят к нему во «Входящие», об этом его уведомляет сам ПланФикс.

Отдельной роли администратора нет: управление пользователями входит в роль руководителя. Сотрудник, приглашённый руководителем, автоматически становится его подчинённым, и заявки этого сотрудника приходят на согласование именно ему.

**Разделение ответственности:** руководитель решает, *нужна ли была трата*, бухгалтер проверяет, *правильно ли она оформлена*. Бухгалтер не может отменить решение руководителя, руководитель не может отметить выплату.

## 4. Пользовательские сценарии

### Путь одной заявки

Основной («счастливый») путь заявки от чека до выплаты. Ветки «Отклонено», «Уточнение» и «Требует доработки» описаны в разделах 4.3–4.5 и 5.

```
Сотрудник жмёт «Отправить» в боте
   │
   ▼  бот → REST API (от имени робота «Payback»)
Задача «Расход» + поля + фото, исполнитель — руководитель сотрудника
   │
   ├─▶ Руководитель: кнопка в боте  ИЛИ  «Входящие» в ПланФиксе
   │        статус → «Одобрено»
   ▼  сценарий ПланФикса передаёт задачу группе «Бухгалтеры»
Бухгалтер: «Входящие» в ПланФиксе
   │   проверяет фото и поля → «К выплате» → платит → «Компенсировано»
   ▼  вебхук → бот
Сотрудник получает уведомление в Telegram
   │
   ▼
Задача попадает в отчёты по категориям, направлениям затрат и сотрудникам
```

### 4.1. Подключение сотрудника

**Первый руководитель.** Telegram ID первого руководителя (обычно владельца) указывается в переменной окружения `OWNER_TELEGRAM_ID` при развёртывании. При первом `/start` этот пользователь автоматически получает роль руководителя. Других способов стать руководителем без приглашения нет.

**Приглашение по ссылке:**

1. Руководитель выполняет в боте `/invite` и выбирает, кого приглашает: сотрудника или другого руководителя.
2. Бот выдаёт одноразовую ссылку вида `t.me/payback_assistant_bot?start=<код>`, действующую 72 часа. Руководитель пересылает её человеку любым удобным способом.
3. Новый пользователь переходит по ссылке, бот просит ввести имя и фамилию.
4. Бот сохраняет привязку «Telegram ID → роль → руководитель» и показывает меню, соответствующее роли. Руководителем приглашённого сотрудника становится тот, кто создал ссылку.
5. Руководитель получает уведомление: «Иван Петров подключился как сотрудник».

**Ограничения:**

- код одноразовый: повторный переход по ссылке или переход другим человеком отклоняется;
- руководитель может отозвать неиспользованную ссылку, деактивировать и снова включить своих сотрудников через `/staff`;
- деактивированный пользователь не может пользоваться ботом, но его прошлые заявки остаются в ПланФиксе; повторный инвайт не нужен — достаточно «Включить» в `/staff`.

### 4.2. Подача заявки

Заявку подаёт сотрудник в личном чате с ботом. Есть два пути: с фото чека (основной) и без чека.

#### 4.2.1. Начало

| Действие сотрудника | Что делает бот |
|---|---|
| Отправляет фото или файл-изображение в любой момент | Начинает подачу заявки с чеком (4.2.2) |
| Нажимает «Трата без чека» в главном меню | Начинает подачу без чека (4.2.7) |
| Отправляет фото, когда уже заполняет другую заявку | Спрашивает: «Начать новую заявку и отменить текущую?» |

Допустимые форматы: JPEG, PNG (как фото или как файл), размер до 15 МБ. На другой тип файла бот отвечает: «Пришлите фото чека в формате JPG или PNG».

#### 4.2.2. Распознавание чека

1. Бот отвечает «Распознаю чек…» и ищет на фото QR-код. Распознавание идёт в отдельном потоке и не блокирует бота.
2. **QR найден.** Из строки QR бот берёт сумму, дату и время покупки, ФН, ФД и ФП и показывает сотруднику: «Чек на 1 250,00 ₽ от 28.09.2026 15:30».
3. **QR не найден или не читается.** Бот предлагает:
   - «Переснять» — сотрудник отправляет новое фото;
   - «Ввести вручную» — бот спрашивает сумму, затем дату покупки. Фото остаётся в заявке, фискальные данные пустые.

Проверки распознанных и введённых данных:

| Проверка | Сообщение при ошибке |
|---|---|
| Сумма — число больше 0 и не больше `MAX_AMOUNT` | «Сумма должна быть от 0,01 до … ₽» |
| Дата не в будущем | «Дата покупки не может быть в будущем» |
| Чек не старше `MAX_RECEIPT_AGE_DAYS` (по умолчанию 90 дней) | «Чек старше 90 дней. Обратитесь к руководителю» |

#### 4.2.3. Проверка на дубликат

Если распознаны ФН, ФД и ФП, бот ищет заявку с такими же данными в своей базе.

- Чек уже подавали: «Этот чек уже подан 12.09.2026 (заявка №26, статус: Одобрено)». Подача завершается.
- Отклонённый ранее чек подать повторно нельзя. Исправимые замечания руководитель решает через «Уточнение», а не через отказ.

Для заявок без фискальных данных проверка на дубликат не выполняется.

#### 4.2.4. Уточняющие вопросы

Бот задаёт вопросы по одному, варианты — кнопками:

1. **Категория** — записи справочника «Категории расходов». Обязательна.
2. **Направление затрат** — записи справочника «Направления затрат» и кнопка «Без направления». Если справочник пуст, вопрос пропускается.
3. **Комментарий** — свободный текст или кнопка «Пропустить».

Списки берутся из ПланФикса и кэшируются не дольше 10 минут.

#### 4.2.5. Подтверждение

Бот показывает итоговую карточку:

```
Заявка на расход
Сумма:        1 250,00 ₽
Дата:         28.09.2026
Категория:    Материалы
Направление:  Ленина, 5
Комментарий:  Саморезы для объекта
Чек:          распознан

[Отправить]  [Исправить]  [Отменить]
```

«Исправить» открывает выбор поля (сумма, дата, категория, направление, комментарий) и возвращает к карточке. Сумму и дату, распознанные по QR, изменить нельзя.

#### 4.2.6. Создание задачи в ПланФиксе

После нажатия «Отправить» бот от имени робота «Payback»:

1. сохраняет заявку в своей базе со статусом «Ожидает отправки»;
2. создаёт задачу: `POST /task/` с Объектом «Расход», полями карточки и исполнителем — руководителем сотрудника (см. 4.6). В заголовке `Idempotency-Key` передаётся ключ, вычисленный из ID заявки в базе бота, поэтому повторная отправка не создаёт дубль;
3. загружает фото: `POST /file/` → ID файла;
4. прикрепляет файл к задаче: `POST /file/{id}/attach/task?id={номер задачи}`;
5. сохраняет номер задачи и ID файла, меняет локальный статус на «На согласовании»;
6. отвечает сотруднику: «Заявка №35 отправлена на согласование»;
7. отправляет руководителю сообщение с данными заявки, фото и кнопками (4.3).

Если сбой случился между шагами 2–4, фоновая задача доделывает только недостающие шаги: по сохранённым номеру задачи и ID файла видно, что уже выполнено.

Название задачи: «Расход: <сумма> ₽, <категория> — <сотрудник>».

Задача создаётся сразу в статусе «На согласовании» — это начальный статус Объекта «Расход».

#### 4.2.7. Заявка без чека

Для трат, по которым кассового чека нет: такси, перевод частному лицу, парковка, утерянный чек. Доступна, если `ALLOW_NO_RECEIPT=true`.

1. Сотрудник нажимает «Трата без чека».
2. Бот спрашивает сумму и дату покупки (проверки — как в 4.2.2). Если задан `NO_RECEIPT_MAX_AMOUNT` и сумма больше него, бот отказывает: «Без чека можно подать трату до … ₽».
3. Категория и направление — как в 4.2.4.
4. **Комментарий обязателен:** что куплено и почему нет чека.
5. Бот предлагает приложить подтверждение (скриншот перевода или поездки): «Отправить фото» или «Пропустить».
6. Подтверждение и создание задачи — как в 4.2.5 и 4.2.6. В задаче ставится флажок «Без кассового чека», фискальные данные пустые. Руководитель видит в сообщении пометку «⚠️ Без кассового чека».

#### 4.2.8. Отмена и сбои

| Ситуация | Поведение |
|---|---|
| Сотрудник нажал «Отменить» или отправил `/cancel` | Черновик удаляется, бот возвращается в главное меню |
| Сотрудник не отвечает 24 часа | Черновик удаляется, бот сообщает: «Заявка не отправлена, начните заново» |
| ПланФикс недоступен при отправке | Заявка остаётся в статусе «Ожидает отправки», бот отвечает: «Заявка принята, отправим её, как только ПланФикс станет доступен». Фоновая задача повторяет отправку; после успеха сотрудник получает номер заявки |
| У сотрудника нет руководителя, связанного с ПланФиксом | Задача создаётся без исполнителя (в ПланФиксе её не будет ни в чьих «Входящих»), бот уведомляет руководителя в Telegram; согласование идёт только через бота |
| Справочник категорий пуст или недоступен | Бот отвечает: «Категории не настроены, обратитесь к руководителю» и прекращает подачу |

### 4.3. Согласование руководителем

1. Руководитель получает сообщение: сотрудник, сумма, категория, направление затрат, комментарий и фото чека.
2. Кнопки:
   - **«Одобрить»** → статус «Одобрено»;
   - **«Отклонить»** → бот просит причину → статус «Отклонено», причина пишется комментарием в задачу;
   - **«Вопрос»** → бот просит текст вопроса → статус «Уточнение», вопрос пишется комментарием в задачу и уходит сотруднику.
3. Бот меняет статус через API (`POST /task/{id}`), сотрудник получает уведомление.
4. Если руководитель принял решение в ПланФиксе, бот убирает кнопки в своём сообщении, чтобы не было двойного решения (подробнее в 4.6).

### 4.4. Уточнение

1. Сотрудник получает вопрос руководителя и отвечает текстом или фото.
2. Ответ добавляется комментарием в задачу (фото — файлом), бот возвращает статус в «На согласовании» и заново отправляет руководителю сообщение с кнопками.

### 4.5. Работа бухгалтера

Бухгалтер работает только в ПланФиксе.

1. После одобрения сценарий ПланФикса передаёт задачу группе «Бухгалтеры» (см. 4.6): она появляется у бухгалтера во «Входящих».
2. Бухгалтер проверяет заявку и:
   - переводит её в «К выплате»;
   - или переводит в «Требует доработки» с комментарием. Бот по вебхуку пересылает сотруднику комментарий бухгалтера. Сотрудник отвечает текстом или фото, бот добавляет ответ в задачу и возвращает статус «Одобрено».
3. После перечисления денег бухгалтер ставит статус «Компенсировано», и сотрудник получает уведомление в бот.

Переход в «К выплате» сотруднику не сообщается: это внутренний шаг бухгалтерии.

### 4.6. Руководитель в ПланФиксе

Основную работу руководитель выполняет в боте. ПланФикс нужен ему для **обзора, анализа и ведения справочников**. Работа в ПланФиксе для руководителя необязательна: всё обязательное (согласование, приглашения) доступно в боте.

#### Что руководитель делает в ПланФиксе

**1. Смотрит отчёты.** Это главная причина открывать ПланФикс:

| Отчёт | Вопрос, на который он отвечает |
|---|---|
| Расходы за месяц по категориям | На что уходят деньги: материалы, топливо, такси |
| Расходы по направлениям затрат | Во что обошлась конкретная площадка, проект или направление |
| Расходы по сотрудникам | Кто и сколько тратит |
| Динамика по месяцам (график) | Растут ли траты |
| Отклонённые заявки за период | Кто чаще подаёт сомнительные траты |

Все отчёты можно фильтровать по периоду и выгружать в Excel.

**2. Разбирает конкретную заявку.** Открывает карточку задачи, чтобы посмотреть фото чека в полном размере, историю комментариев и фискальные данные. Из карточки видно, кто и когда принял решение.

**3. Согласует пачкой.** Если заявок много, руководитель может работать во «Входящих» и менять статусы прямо в ПланФиксе. Бот узнаёт о решении по вебхуку и:
- убирает кнопки из сообщения руководителя в Telegram и дописывает «Решение принято в ПланФиксе»;
- уведомляет сотрудника так же, как при решении в боте.

Если руководитель отклоняет заявку или задаёт вопрос в ПланФиксе, причина или вопрос пишется комментарием к задаче. Бот пересылает сотруднику последний комментарий руководителя вместе с уведомлением о смене статуса.

**4. Ведёт справочники.** Добавляет новое направление затрат, когда начинается работа на новой площадке или проекте, скрывает закрытые, правит список категорий. Бот читает справочники через API, поэтому кнопки у сотрудников обновляются без перезапуска. Кэш справочников в боте живёт не дольше 10 минут.

#### Что руководитель НЕ делает в ПланФиксе

- Не создаёт заявки: их создаёт только бот.
- Не приглашает и не отключает сотрудников: это делается в боте через `/invite` и `/staff`.
- Не отмечает выплату: это зона бухгалтера.
- Не редактирует карточку заявки: роль «Исполнитель» в ПланФиксе меняет статус, но не поля. Исправить категорию или направление может администратор аккаунта (обычно владелец).

#### Доступ руководителя к заявкам

Все задачи создаёт служебный робот «Payback», а автоматический доступ руководителя к задачам подчинённых есть только на Plan B. Поэтому доступ и разделение ответственности настраиваются явно, через **эстафету исполнителя** (проверено на тестовом аккаунте):

```
На согласовании        исполнитель = руководитель сотрудника   → одобряет / отклоняет / уточняет
      │  сценарий «Передать бухгалтеру» (при переходе в «Одобрено»):
      │    1) добавить участника: группа «Руководители»
      │    2) отстранить всех исполнителей
      │    3) добавить исполнителя: группа «Бухгалтеры»
      ▼
Одобрено → К выплате → Компенсировано   исполнитель = группа «Бухгалтеры»   → проверяет и выплачивает
```

1. У руководителя в локальной базе бота хранится `planfix_user_id` — связь с его пользователем в ПланФиксе.
2. При создании задачи бот через API назначает **исполнителем** руководителя сотрудника. Заявка попадает к нему во «Входящие» — это и есть список «Ждут моего решения».
3. Права на **каждый переход** статусов Объекта «Расход» выдаются **роли «Исполнитель»**. Поэтому статус меняет только тот, у кого заявка сейчас «на руках»: руководитель не может отметить выплату, бухгалтер не может одобрить трату.
4. При переходе в «Одобрено» сценарий добавляет **участником группу «Руководители»**, **отстраняет всех исполнителей** и **добавляет исполнителем группу «Бухгалтеры»**. Участник видит задачу (не во «Входящих», а в общем списке), может комментировать, но не может менять статус. Сценарий универсален: работает при любом исполнителе (конкретный руководитель, группа, другой сотрудник), имена людей в нём не упоминаются.
5. **Видимость:** пока заявка на согласовании, её видит только руководитель этого сотрудника (он исполнитель). После одобрения её видят все руководители (участники) и все бухгалтеры (исполнители). Для малого бизнеса с одним-двумя руководителями это приемлемо; если нужно, чтобы одобренные заявки видел только «свой» руководитель, бот может при создании задачи добавлять участником конкретного руководителя вместо группы (roadmap).

**Почему именно так (проверено на практике):** действие «Вместо исполнителя: X → Y» заменяет только конкретного исполнителя X. Когда в ручном тесте исполнителем была группа «Руководители», замена срабатывала, а у задачи из API с исполнителем `user:3` — нет. Связка «отстранить всех исполнителей + добавить группу» не зависит от того, кто был исполнителем.

Бот выполняет действия от имени робота-администратора, поэтому права ПланФикса на переходы его не ограничивают: при нажатии кнопок в Telegram права проверяет сам бот (см. раздел 9).

**Связь с пользователем ПланФикса** настраивается в боте: руководитель в `/staff` нажимает «Связать с ПланФиксом», бот показывает список пользователей аккаунта (`POST /user/list`), руководитель выбирает себя. Без этой связи руководитель работает только в боте, а заявки его сотрудников до одобрения в ПланФиксе видит только администратор аккаунта.

#### Руководители без места в ПланФиксе

Каждый пользователь ПланФикса — платное место. Если в компании несколько руководителей (например, три прораба), в v1 поддерживается такая схема:

- **владелец** работает и в боте, и в ПланФиксе (отчёты, справочники);
- **остальные руководители** работают только в боте: согласуют заявки своих сотрудников и приглашают людей;
- в ПланФиксе у них нет места, связь `planfix_user_id` не заполняется.

Отчёт для руководителей прямо в боте (`/report`) — в roadmap.

## 5. Статусы заявки

| Статус | Кто переводит дальше | Возможные переходы | Уведомление в бот |
|---|---|---|---|
| **На согласовании** | Руководитель | → Одобрено, Отклонено, Уточнение | руководителю: новая заявка |
| **Уточнение** | Сотрудник (ответом в боте) | → На согласовании | сотруднику: вопрос руководителя |
| **Отклонено** | — | конечный | сотруднику: причина отказа |
| **Одобрено** | Бухгалтер | → К выплате, Требует доработки | сотруднику |
| **Требует доработки** | Сотрудник (ответом в боте) | → Одобрено | сотруднику: комментарий бухгалтера |
| **К выплате** | Бухгалтер | → Компенсировано | — |
| **Компенсировано** | — | конечный | сотруднику |

Итого 7 статусов. Статусы и права на переходы задаются в Объекте «Расход» в ПланФиксе и дополнительно проверяются ботом.

В базе бота у заявки есть ещё один, локальный статус — **«Ожидает отправки»**: заявка подтверждена сотрудником, но задача в ПланФиксе ещё не создана.

## 6. Данные заявки (карточка Объекта «Расход»)

| Поле | Тип в ПланФиксе | Заполняет |
|---|---|---|
| Сотрудник (подал) | строка (имя и фамилия из бота) | бот |
| Сумма | число, 2 знака после запятой | бот (QR или ручной ввод) |
| Дата покупки | дата | бот |
| Категория | запись справочника «Категории расходов» | сотрудник |
| Направление затрат | запись справочника «Направления затрат» | сотрудник |
| ФН, ФД, ФП | строки | бот (из QR) |
| Без кассового чека | флажок | бот |
| Дата выплаты | дата | бухгалтер |

Фото чека прикрепляется к задаче файлом. Комментарии сотрудника, вопросы и ответы — комментарии задачи.

Сотрудники не заводятся в ПланФиксе ни как пользователи, ни как записи справочника: в задаче хранится только имя строкой, а связь «заявка → человек в Telegram» живёт в базе бота.

## 7. Настройка ПланФикса

Выполняется администратором аккаунта один раз, в README будет пошаговая инструкция со скриншотами.

> **Термины ПланФикса.** **Объект** — тип задачи со своей карточкой (набор полей), набором статусов, автоматическими сценариями и кнопками; в терминах разработки это модель и конечный автомат одновременно. **Шаблон задачи** — заготовка с заранее заданными значениями для быстрого создания задач. Связка «шаблон задачи + процесс» — устаревший способ описания задач, который ПланФикс сохраняет для совместимости; в решении используется Объект. Чтобы не путаться с термином «Объект», справочник мест и проектов, к которым относятся траты, называется «Направления затрат».

1. **Робот «Payback»** (Сотрудники → Роботы → «Новый робот»), от имени которого бот работает через API. Роботы бесплатны — не занимают платное место — и имеют права администратора. Для робота выпускается токен REST API; робот становится постановщиком всех задач, созданных ботом (проверено).
   Уровни доступа токена: чтение, создание и изменение задач; чтение и добавление комментариев; добавление и чтение файлов; чтение сотрудников; чтение справочников.
2. **Рабочие группы «Бухгалтеры» и «Руководители»** (Сотрудники → Рабочие группы) с включённой галочкой «Отображать в списках выбора исполнителей и участников»; галочку «Разрешить контактам ставить задачи этой группе» не включать. Клиент добавляет в группы своих бухгалтеров и руководителей — сценарии перенастраивать не нужно.
3. **Справочники** «Категории расходов» и «Направления затрат». В каждом одно поле «Название» (столбец), категории и направления — записи (строки).
4. **Объект «Расход»**, который описывает тип задачи «заявка на расход»:
   - **карточка** — пользовательские поля из раздела 6. У поля «Дата покупки» отключить автозаполнение текущей датой, у поля «Категория» — запрет дубликатов;
   - **набор статусов** — 7 статусов из раздела 5, начальный — «На согласовании»; права на **каждый переход** — только роли «Исполнитель»;
   - **сценарий «Передать бухгалтеру»** — событие «Задача изменена и стала соответствовать условиям», условие «Статус = Одобрено», от имени постановщика; действия по порядку: добавить участника — группа «Руководители»; отстранить всех исполнителей; добавить исполнителя — группа «Бухгалтеры» (см. 4.6);
   - **сценарии-вебхуки** — по одному на каждый статус, о котором должен узнать бот: «Уточнение», «Отклонено», «Одобрено», «Требует доработки», «Компенсировано». Событие и условие — как в сценарии выше, действие — HTTP-запрос (см. ниже).
5. **Фильтры и отчёты:**
   - руководитель: «Входящие» (заявки, где он исполнитель), отчёты из раздела 4.6;
   - бухгалтер: «Входящие», «К выплате», «Требует доработки», «Реестр за период» с выгрузкой в Excel.

Всего 6 сценариев при лимите Plan A в 15 на Объект.

**Вебхук.** Один сценарий на статус нужен потому, что событие «стала соответствовать условиям» не сработает при переходе между двумя статусами из одного списка в условии. Запрос:

```
POST https://<адрес сервиса>/webhooks/planfix
Content-Type: application/json

{"task": 34, "secret": "<WEBHOOK_SECRET>", "status": "Одобрено"}
```

В настройке действия параметры задаются парами «имя — значение»: `task` — номер задачи (переменная), `secret` — строка, `status` — название статуса (переменная). Номер задачи в вебхуке совпадает с ID задачи в REST API.

### 7.1. Совместимость с Plan A

**Минимальный тариф — Plan A**, самый дешёвый платный тариф (около 463 ₽ за пользователя в месяц). На бесплатном тарифе решение не работает: не хватает статусов и полей, а REST API доступен только в платных аккаунтах.

Платные места: владелец, бухгалтер и те руководители, которым нужен ПланФикс. Робот и сотрудники, работающие через бота, мест не занимают.

Решение **намеренно не использует** возможности, которых нет на Plan A, чтобы клиенту не пришлось переходить на более дорогой тариф:

| Возможность ПланФикса (нет на Plan A) | Чем заменено в решении |
|---|---|
| Кнопки и группы кнопок в Объекте | Статусы меняются стандартным способом в ПланФиксе; кнопки для руководителя есть в боте |
| Вычисляемые поля задач, поля «Итоги аналитик» | Все вычисления выполняет бот |
| Связанные поля | Категория и направление затрат хранятся как ссылки на записи справочников |
| Формирование отчётов по API | Бот получает список задач за период через REST API и сам считает суммы (для `/report` и сводок) |
| Автоматическое выполнение отчётов по расписанию | Периодические сводки рассылает бот |
| Структура компании, руководители групп, автоматический доступ руководителей к задачам подчинённых | Доступ задаётся явно: бот назначает руководителя исполнителем, сценарий передаёт заявку группе «Бухгалтеры» (эстафета исполнителя, см. 4.6) |

Что решение **использует**, и всё это доступно на Plan A: Объекты с пользовательскими полями и набором статусов, права на переходы между статусами, автоматические сценарии с HTTP-запросами, справочники, рабочие группы, роботы, фильтры, обычные отчёты, REST API.

**Правило для разработки:** пробный период ПланФикса открывает все возможности, включая недоступные на Plan A. При настройке тестового аккаунта нельзя использовать возможности из таблицы выше, иначе у клиента на Plan A решение перестанет работать. Полный список ограничений — в [`planfix-notes.md`](planfix-notes.md).

## 8. Архитектура

```
┌──────────────┐    updates     ┌─────────────────────────────┐    REST API    ┌────────────┐
│   Telegram   │ ─────────────▶ │           Payback           │ ─────────────▶ │  ПланФикс  │
│  (сотрудники │ ◀───────────── │  aiogram 3  │    FastAPI    │ ◀───────────── │            │
│ руководители)│    сообщения   │   (бот)     │  (вебхуки)    │    вебхуки     │            │
└──────────────┘                │         SQLAlchemy          │                └────────────┘
                                │     PostgreSQL / SQLite     │
                                └─────────────────────────────┘
```

### Стек

- **Python 3.12**
- **aiogram 3** — бот, FSM для диалогов
- **FastAPI + Uvicorn** — приём вебхуков ПланФикса и эндпоинт `/health`
- **SQLAlchemy 2.0 (async) + Alembic** — база и миграции
- **PostgreSQL** — прод и локальная разработка по умолчанию; **SQLite** — опциональный fallback (`DATABASE_URL` / `make test-sqlite`), без гарантии полного паритета
- **httpx** — асинхронный клиент к REST API ПланФикса
- **Pydantic v2** — валидация данных и настроек (`pydantic-settings`)
- **pyzbar + OpenCV (headless)** — распознавание QR
- **pytest + pytest-asyncio + respx** — тесты
- **Docker + docker compose**

### Модули

```
payback/
├── bot/            # хендлеры aiogram, клавиатуры, FSM-состояния
├── api/            # FastAPI: вебхуки от ПланФикса, /health
├── planfix/        # клиент REST API: задачи, поля, файлы, комментарии, справочники
├── receipts/       # распознавание QR, парсинг фискальной строки
├── services/       # бизнес-логика: подача, согласование, уведомления
├── db/             # модели SQLAlchemy, репозитории, миграции
├── config.py       # настройки из переменных окружения
└── main.py         # запуск бота и FastAPI в одном процессе
```

Бот и FastAPI работают в одном процессе и одном event loop: Uvicorn запускает FastAPI, а polling aiogram стартует как фоновая задача в `lifespan`. Так обработчик вебхука может напрямую вызвать `bot.send_message`, и не нужен брокер сообщений между двумя сервисами.

Бизнес-логика живёт в `services/` и не зависит ни от aiogram, ни от httpx: клиент ПланФикса и отправка уведомлений передаются в сервисы как зависимости. Это позволяет тестировать сценарии с подменами (раздел 10).

### Запуск

1. Чтение настроек из переменных окружения.
2. Проверка схемы ПланФикса: бот запрашивает поля задач (`GET /customfield/task`) и убеждается, что все ID из настроек существуют и имеют ожидаемый тип; ID справочников берутся из описания полей «Категория» и «Направление затрат». При несоответствии сервис не стартует и пишет в лог, чего не хватает.
3. Запуск FastAPI, затем polling бота.

Справочники читаются по первому обращению и хранятся в памяти 10 минут. Если ПланФикс недоступен, бот отдаёт последнюю успешно загруженную версию. `/refresh` сбрасывает кэш вручную.

### Обработка вебхука

1. `POST /webhooks/planfix` проверяет секрет (сравнение за постоянное время) и **сразу отвечает 200**. ПланФикс отправляет запросы в один поток и при ответе, отличном от 200, повторяет их до четырёх раз, поэтому медленный или ошибочный ответ тормозит всю очередь.
2. Обработка идёт в фоновой задаче: бот заново читает задачу через API (`GET /task/{id}`) и не доверяет статусу из тела запроса.
3. Если статус задачи совпадает с локальным, событие игнорируется. Так отсекаются повторы и «эхо» — вебхуки на изменения, которые сделал сам бот.
4. Иначе бот обновляет локальный статус, читает последний комментарий (если он нужен для уведомления), уведомляет сотрудника и убирает кнопки у руководителя.

При остановке сервис дожидается завершения фоновых задач.

### Локальная база данных

Бот хранит только то, чего нет в ПланФиксе или что нужно для быстрой работы:

- **users** — Telegram ID, имя, роль (сотрудник или руководитель), ID руководителя, `planfix_user_id` (может быть пустым), активен ли, дата подключения;
- **invites** — код, роль, кто создал, срок действия, кем и когда использован;
- **expenses** — ID сотрудника, ID задачи в ПланФиксе, статус, сумма, дата покупки, категория, направление, комментарий, ФН/ФД/ФП (уникальный индекс), признак «без чека», `telegram_file_id` фото, ID файла в ПланФиксе, ID сообщения руководителю в Telegram (чтобы убирать кнопки), даты создания и изменения.

Источник истины по статусу заявки — ПланФикс. Локальный статус — это кэш, который обновляется по вебхукам.

**Срок хранения:** заявки хранятся бессрочно, незавершённые черновики удаляются через 24 часа. Состояние диалога (FSM) в v1 хранится в памяти.

**Миграции:** Alembic; схема создаётся и обновляется командой `alembic upgrade head` при запуске контейнера.

## 9. Нефункциональные требования

**Надёжность**
- Запросы к ПланФиксу повторяются при сетевых ошибках и ответах 5xx с экспоненциальной задержкой (до 3 попыток). Ответ 202 (изменение поставлено в очередь) считается успехом.
- Если ПланФикс недоступен при подаче чека, заявка сохраняется локально со статусом «Ожидает отправки» и отправляется повторно фоновой задачей. Сотрудник видит понятное сообщение, а не ошибку.
- Повторное нажатие кнопки или повторный вебхук не создают дублей и не меняют статус дважды: задача создаётся с `Idempotency-Key`, вебхук сравнивается с локальным статусом.

**Производительность**
- Распознавание QR выполняется через `asyncio.to_thread`, чтобы не блокировать бота.
- Ответ бота на нажатие кнопки — не дольше 2 секунд в нормальных условиях.
- Эндпоинт вебхука отвечает сразу, обработка идёт в фоне.

**Валидация**
- Сумма > 0 и ≤ настраиваемого максимума, дата не в будущем и не старше настраиваемого срока (по умолчанию 90 дней).
- Размер фото ≤ 15 МБ, форматы JPEG и PNG.

**Безопасность**
- Все секреты (токен бота, токен ПланФикса, секрет вебхука) — только в переменных окружения; в логи не выводятся.
- Входящие вебхуки проверяются по секрету в теле запроса, запросы без него отклоняются с кодом 403.
- Бот проверяет роль пользователя перед каждым действием: сотрудник видит только свои заявки, руководитель — только заявки своих сотрудников.
- Фото чеков не хранятся на сервере: в базе лежит только идентификатор файла в Telegram.

**Наблюдаемость**
- Структурированные логи (JSON) с ID заявки и ID задачи ПланФикса.
- Эндпоинт `/health` для проверки состояния.

**Развёртывание**
- Один `docker compose up -d` поднимает сервис и PostgreSQL.
- Требования к серверу: 1 vCPU, 1 ГБ RAM.
- Для вебхуков ПланФикса нужен публичный HTTPS-адрес (reverse proxy Caddy или аналог в docker compose).

### Переменные окружения

| Переменная | Назначение |
|---|---|
| `BOT_TOKEN` | Токен Telegram-бота |
| `OWNER_TELEGRAM_ID` | Telegram ID первого руководителя |
| `PLANFIX_ACCOUNT` | Адрес аккаунта ПланФикса, например `https://example.planfix.ru` |
| `PLANFIX_API_TOKEN` | Токен REST API робота «Payback» |
| `PLANFIX_OBJECT_ID` | ID Объекта «Расход» |
| `PLANFIX_FIELD_*` | ID пользовательских полей (сумма, дата покупки, категория, направление, сотрудник, ФН, ФД, ФП, без чека) |
| `PLANFIX_STATUS_*` | ID статусов Объекта «Расход» |
| `WEBHOOK_SECRET` | Секрет для проверки входящих вебхуков |
| `DATABASE_URL` | Строка подключения к БД |
| `MAX_AMOUNT`, `MAX_RECEIPT_AGE_DAYS` | Ограничения валидации |
| `ALLOW_NO_RECEIPT` | Разрешить заявки без чека (`true`/`false`) |
| `NO_RECEIPT_MAX_AMOUNT` | Максимальная сумма заявки без чека; пусто — без ограничения |
| `DEV_MODE` | Режим разработки: разрешает fallback на FakePlanfix при недоступном ПланФиксе. В продакшене выключен |

В репозитории лежит `.env.example` с пустыми значениями; сам `.env` в репозиторий не попадает.

## 10. Тестирование

**Автоматические тесты**

- Юнит-тесты: парсинг фискальной строки, валидация, переходы статусов, проверка прав.
- Тесты сервисов с подменами `FakePlanfix` и `FakeNotifier`: вся подача, согласование и обработка вебхука проверяются без Telegram и без сети.
- Тесты клиента ПланФикса на `respx` с ответами, сохранёнными из настоящего API (`tests/fixtures/`).
- Тесты хендлеров через `dp.feed_raw_update` с подставленными обновлениями Telegram — для основных диалогов.
- Набор тестовых чеков: собственные фото и синтетические чеки со сгенерированными QR (скрипт `scripts/generate_receipts.py`).

**Ручная проверка**

- Для ручной проверки ролей используйте отдельные Telegram-аккаунты сотрудника и руководителя.
- Роли в ПланФиксе (владелец, руководитель, бухгалтер) открываются в отдельных контейнерах Firefox Multi-Account Containers.
- Полный прогон на пробном аккаунте ПланФикса перед релизом.

## 11. Что не входит в v1

- Бухгалтер в боте (уведомления, сводки).
- Учёт выданных авансов и баланса по подотчёту.
- Интеграция с конфигурацией «Учет доходов и расходов».
- Мессенджеры кроме Telegram.
- Работа с несколькими аккаунтами ПланФикса в одном экземпляре сервиса.
- Режим, в котором у сотрудников есть собственные аккаунты в ПланФиксе.
- OCR чеков без QR-кода, фото в формате HEIC.
- Интеграция с 1С.

## 12. Открытые вопросы

Решено:

- [x] Сотрудники в ПланФиксе не заводятся; в задаче — строковое поле «Сотрудник».
- [x] Задача создаётся `POST /task/` с `"object": {"id": …}` и массивом `customFieldData`.
- [x] Руководитель назначается исполнителем; после одобрения сценарий передаёт задачу бухгалтерам (эстафета, 4.6).
- [x] Токен REST API выпускается для робота; робот становится постановщиком задач.
- [x] Вебхук: POST с JSON `{"task", "secret", "status"}`, секрет в теле запроса.
- [x] Файл: `POST /file/`, затем `POST /file/{id}/attach/task?id=…`.
- [x] REST API есть только на платных тарифах; HTTP-запросы из сценариев — на всех.
- [x] Цена Plan A — около 463 ₽ за пользователя в месяц.

Осталось проверить:

- [ ] «Эхо»: приходит ли вебхук, когда статус меняет сам бот через API. Архитектура к этому готова (сравнение с локальным статусом), проверка нужна для тестов.
- [ ] Формат ответа `POST /task/{id}/comments/list`: как отличить комментарий человека от служебного и кто автор.
- [ ] ID остальных статусов Объекта «Расход».
- [ ] Отчёты и фильтры для бухгалтера: собрать в интерфейсе и описать в инструкции.
- [ ] Оплачиваются ли сотрудники в статусе «Активен (нет доступа)».
- [ ] Требования официального каталога ПланФикса к решениям и можно ли использовать название «ПланФикс».

## 13. Roadmap

**v1.1 — Подотчёт**
- Учёт выданных авансов, баланс по каждому сотруднику, расчёт перерасхода и остатка.
- Бухгалтер в боте: сводные уведомления об одобренных заявках, напоминания о «К выплате».
- Напоминания руководителю о зависших заявках через сутки.
- Автоодобрение трат до настраиваемой суммы.

**v1.2 — Интеграция с учётом**
- Запись одобренных трат в конфигурацию «Учет доходов и расходов» (справочники и аналитики).
- Еженедельная и ежемесячная сводка владельцу в Telegram (считается ботом по списку задач, так как отчёты по API и по расписанию недоступны на Plan A).
- Выгрузка реестра в Excel/CSV из бота.
- Команда `/report` для руководителей: сводка за период по своим сотрудникам, категориям и направлениям затрат прямо в Telegram (для руководителей без места в ПланФиксе).
- Видимость одобренных заявок только для «своего» руководителя.

**v1.3 — Качество распознавания**
- Детектор WeChat QR для плохих фото.
- Проверка чека через сервис ФНС (подлинность, список товаров).
- OCR для чеков без QR, поддержка HEIC.

**v2 — Масштабирование**
- Поддержка MAX.
- Режим с аккаунтами сотрудников в ПланФиксе.
- Мультиаккаунтный режим (один сервис для нескольких компаний).
- Выгрузка в 1С.
- Автоочистка старых заявок как настройка.
